# Chari Pay SDK — Design

**Date:** 2026-09-10
**Status:** Approved (design); implementation plan pending
**Package:** `@chari-pay/sdk`
**Repo:** new sibling repo `../chari-pay-sdk`
**Source of truth:** `api-1.yaml` (OpenAPI 3, 62 operations) from the `example_psp` tester app

---

## 1. Purpose

A framework-agnostic TypeScript SDK that makes integrating the Chari Pay PSP a
five-line job in Express, NestJS, Next.js, Fastify, or plain Node — replacing
the hand-rolled HTTP plumbing that every integrator currently rewrites (auth
header, error envelope, idempotency, webhook HMAC, pagination).

The `example_psp` NestJS tester app is the reference for behaviour that is
already proven in production-style use; it becomes a consumer of the SDK rather
than a template to copy.

### Success criteria

1. A merchant can create a payment link and collect a payment with a
   `new ChariPay(key)` and one method call.
2. Verifying a webhook is one call in any framework, and cannot be got wrong by
   forgetting to capture the raw body.
3. Every one of the 62 operations in `api-1.yaml` is reachable through a typed
   method.
4. Zero runtime dependencies; works on Node 18+, Bun, Deno, and edge runtimes.
5. No real API key or webhook secret appears anywhere in the repo.

### Non-goals

- No hosted-checkout UI components, no React bindings.
- No PCI-scope card handling helpers beyond passing through `/checkout/submit`.
- No persistence, queueing, or webhook-replay storage. That is the integrator's.

---

## 2. Approach

**Generated types as a floor, hand-written resources on top.**

`api-1.yaml` documents 62 operations but only 30 success responses — e.g.
`GET /v1/transactions` defines only its 4xx/429 bodies. Pure code generation
would therefore type roughly half the SDK as `unknown`, and pure hand-writing
would drift from the spec on the first API change. So:

- `openapi-typescript` generates `src/generated/api.ts`, regenerated by
  `npm run codegen` and never edited by hand.
- Each resource method is hand-written with an explicit return type: the
  generated schema where the spec has one (`PaymentLinkResponse`,
  `SubscriptionResponse`, `ClientResponse`, …), and a hand-modelled type from
  `src/types/` where it does not.
- Every hand-modelled type carries
  `@remarks Not defined in api-1.yaml; modelled from the endpoint description.`
  so no consumer mistakes it for spec-derived truth. When the spec gains a real
  schema, the gap type is deleted and the generated one takes over.

Rejected alternatives: pure codegen (half the surface returns `unknown`, DX
worse than the existing tester app); fully hand-written (no mechanical link to
the spec, drifts immediately).

## 4. The client

```ts
import { ChariPay } from '@chari-pay/sdk';

const chari = new ChariPay(process.env.CHARI_PAY_API_KEY!);

const link = await chari.paymentLinks.create({
  amount: 149.9,
  description: 'Order #1234',
  acceptUrl: 'https://shop.example.com/success',
  declineUrl: 'https://shop.example.com/cancel',
});
console.log(link.url);
```

### Configuration

```ts
new ChariPay(apiKey: string)
new ChariPay(config: ChariPayConfig)

interface ChariPayConfig {
  apiKey: string;
  /** Overrides the base URL inferred from the key prefix. */
  baseUrl?: string;
  /** Per-request timeout in ms. Default 30_000. */
  timeout?: number;
  /** Retry attempts for retryable failures. Default 2. */
  maxRetries?: number;
  /** Secret used by `chari.webhooks.constructEvent` when none is passed. */
  webhookSecret?: string;
  /** Custom fetch (tests, proxies, tracing). Default: global fetch. */
  fetch?: typeof fetch;
  /** Observability hooks. */
  onRequest?: (req: RequestInfo) => void;
  onResponse?: (res: ResponseInfo) => void;
}
```

**Environment inference.** A key beginning `chari_sk_test_` resolves to the
sandbox base URL (`https://api-psp.charipay.ma`); anything else
resolves to production (`https://api-psp.charipay.ma`). `baseUrl` overrides. There is
no separate `environment` flag, because a flag that disagrees with the key is a
bug waiting to happen — the key already determines the environment server-side.

### Naming

Stripe's verbs, so the API is guessable: `create`, `retrieve`, `update`,
`list`, `del`, `cancel`, plus domain verbs (`pause`, `resume`, `refund`,
`send`). Resource namespaces are camelCase plurals.

### Paths

Each resource owns its **full path**. The API mixes three prefixes —
`/v1/…`, `/api/v1/partner/webhooks/…`, `/checkout/…` — so a single configured
prefix would be wrong for two thirds of the surface.

### Authentication

`X-CHARI-PAY-API-KEY` on every request **except** the four public
`/checkout/*` operations (`verify`, `submit`, `return`, `payments/{reference}`),
which the spec marks `security: []` and whose descriptions explicitly say "no
API key — do not send X-CHARI-PAY-API-KEY". The `checkout` namespace sets a
`public: true` flag on its requests and `http.ts` omits the header for those.

### Idempotency

Every `create*` method generates a UUID `Idempotency-Key` unless the caller
passes one via per-call options, so a retried POST never double-charges.
`POST /checkout/submit` requires the header for reusable sessions; the SDK
always sends it there.

### Per-call options

Every method takes an optional final `RequestOptions` argument:
`{ idempotencyKey?, requestId?, timeout?, maxRetries?, signal? }`.

## 6. Errors

Chari Pay returns `{ error: { code, message }, correlationId }`. The SDK maps it
to one typed hierarchy:

```ts
class ChariPayError extends Error {
  readonly status: number;          // HTTP status
  readonly code: string;            // e.g. 'VALIDATION_ERROR', 'WALLET_NOT_ACTIVE'
  readonly correlationId?: string;  // quote this to Chari Pay support
  readonly requestId?: string;      // the X-Request-Id we sent
  readonly raw: unknown;            // untouched response body
}
```

| Subclass | Trigger |
| --- | --- |
| `ChariPayAuthenticationError` | 401 `UNAUTHORIZED` |
| `ChariPayPermissionError` | 403 `FORBIDDEN`, `PRODUCTION_ACCESS_DENIED` |
| `ChariPayValidationError` | 400/422 — adds `field?` |
| `ChariPayRateLimitError` | 429 — adds `retryAfter` (seconds) |
| `ChariPayConnectionError` | network failure, DNS, timeout |
| `ChariPayAPIError` | 5xx and anything unmapped |

`toString()` includes `code`, `message`, and `correlationId`, because the
correlation id is the first thing support asks for.

### Retries

Retryable: network errors, timeouts, 429, and 5xx. Retried only when the
request is idempotent (GET/PUT/DELETE) or carries an `Idempotency-Key` — which
every `create*` does. Exponential backoff with full jitter, base 500 ms, capped
at 8 s, `Retry-After` honoured when present. Default `maxRetries: 2`.

## 7. Webhooks

### Verification core (`src/webhooks.ts`)

Ported from `example_psp`'s proven implementation
(`src/webhooks/webhooks.controller.ts`), including its test vectors:

- Signature = `HMAC-SHA256(secret, timestamp + "." + rawBody)`, hex.
- Header `Chari-Webhook-Signature`, with `X-CHARI-SIGNATURE` also accepted —
  during a secret rotation, deliveries carry both.
- Timestamp header `Chari-Webhook-Timestamp` / `X-CHARI-TIMESTAMP`, rejected
  beyond a 5-minute drift (configurable `tolerance`).
- Constant-time comparison via `timingSafeEqual`, and a malformed signature
  must fail cleanly rather than throw a decoding error.

```ts
function verifyWebhookSignature(opts: {
  rawBody: string | Buffer;
  headers: Record<string, string | string[] | undefined>;
  secret: string;
  toleranceMs?: number;   // default 300_000
}): void;                 // throws ChariPaySignatureVerificationError

chari.webhooks.constructEvent(rawBody, headers, secret?): ChariPayEvent;
```

`constructEvent` verifies, then parses, then returns a **discriminated union**
over the 21 event types the spec enumerates:

```
payment.initiated | payment.requires_action | payment.succeeded | payment.failed
refund.initiated | refund.succeeded | refund.failed
payment_link.created | payment_link.updated | payment_link.cancelled | payment_link.expired
subscription.payment_succeeded | subscription.payment_failed | subscription.canceled
wallet.activated | wallet.funded | wallet.rejected | wallet.transfer_completed
security.invalid_signature | security.rate_limit_exceeded | security.token_reused
```

```ts
const event = chari.webhooks.constructEvent(req.rawBody, req.headers, secret);
switch (event.type) {
  case 'payment.succeeded':
    event.data.reference;   // narrowed, no casts
    break;
}
```

An unknown incoming `type` widens to `{ type: string; data: unknown }` rather
than throwing — a new event type on Chari Pay's side must not break a
deployed integration.

**Payload types are hand-modelled.** `api-1.yaml` enumerates the event *names*
and defines `WebhookEventResponse` (the delivery record served by the partner
events API), but it defines no per-event `data` schema. The `data` shapes of
this union therefore live in `src/types/` under the same rule as the 32 gap
responses — each carries the `Not defined in api-1.yaml` remark — and are
verified before `1.0.0` against real sandbox deliveries captured with the
`example_psp` webhook inbox, which exists for exactly this purpose.

### Express adapter

```ts
import { chariPayWebhook } from '@chari-pay/sdk/express';

app.post('/webhooks/chari-pay',
  chariPayWebhook({ secret: process.env.CHARI_PAY_WEBHOOK_SECRET! }),
  (req, res) => {
    if (req.chariPayEvent.type === 'payment.succeeded') { /* … */ }
    res.sendStatus(200);
  },
);
```

The middleware reads the raw bytes off the request stream itself, so it works
whether or not `express.json()` ran first. Forgetting to preserve the raw body
is the single most common webhook integration bug, and the SDK absorbs it
rather than documenting around it. On verification failure it responds `400`
and does not call the handler. `req.chariPayEvent` is declared through module
augmentation so it is typed without casts.

### NestJS adapter

```ts
@Module({
  imports: [ChariPayModule.forRoot({
    apiKey: process.env.CHARI_PAY_API_KEY!,
    webhookSecret: process.env.CHARI_PAY_WEBHOOK_SECRET!,
  })],
})
export class AppModule {}

@Controller('webhooks')
export class WebhooksController {
  constructor(private readonly chari: ChariPay) {}

  @Post('chari-pay')
  @ChariPayWebhook()
  handle(@ChariPayEventPayload() event: ChariPayEvent) { /* … */ }
}
```

`forRoot` and `forRootAsync` provide an injectable `ChariPay`. A guard performs
verification; a param decorator supplies the typed event. The module documents
the `rawBody: true` requirement in `NestFactory.create` and fails loudly at
startup if it is missing, rather than at 3 a.m. on a live delivery.

## 8. Pagination

List endpoints return a Spring-style page (`content`, `totalElements`,
`totalPages`, `number`, `size`); some also accept `cursor`/`limit`. The SDK
returns a `Page<T>` that is both awaitable and async-iterable:

```ts
const page = await chari.transactions.list({ status: 'SUCCESS' });
page.content; page.totalElements;

for await (const tx of chari.transactions.list({ status: 'SUCCESS' })) { … }

const all = await chari.transactions.list().autoPagingToArray({ limit: 500 });
```

`autoPagingToArray` requires an explicit `limit` so nobody accidentally pulls a
year of transactions into memory.

## 9. Binary endpoints

`ribDocument`, `qr`, `poster`, and `exportCsv` return

```ts
interface ChariPayFile {
  data: Buffer;
  contentType: string;       // 'application/pdf', 'image/png', 'text/csv'
  filename?: string;         // from Content-Disposition when present
}
```

with a `.toStream()` helper for piping straight into an HTTP response.

## 10. Developer experience

- **JSDoc generated from the spec.** `api-1.yaml` carries a description and an
  example on nearly every field; codegen carries them into the emitted types so
  hovering `paymentLinks.create` in an editor shows "Amount to collect, in MAD
  major units — e.g. 149.9". Discarding that annotation would be the single
  biggest DX loss available.
- **Guessable surface.** Stripe verbs, one namespace per resource,
  `retrieve(reference)` everywhere the API keys off a reference.
- **Actionable errors.** A `ChariPayValidationError` names the field; a 401
  message says which environment the key resolved to.
- **Debug logging.** `CHARI_DEBUG=1` (or `onRequest`/`onResponse`) logs method,
  URL, status, duration, and correlation id, with API keys, PAN, and CVV
  redacted unconditionally.
- **Cookbook README.** Charge in five lines; hosted checkout; direct-API
  checkout with 3-D Secure; subscriptions; refunds; webhooks per framework;
  a "moving to production" section covering the key prefix and secret rotation.
- **Runnable examples** under `examples/express`, `examples/nestjs`,
  `examples/nextjs`, each a working app driven from a `.env.example` containing
  placeholders only.

### Secrets policy

No real API key or webhook secret ever enters this repo — not in code, tests,
fixtures, README, or examples. The sandbox credentials that exist in
`example_psp/.env` stay there. Tests use obviously fake constants
(`chari_sk_test_EXAMPLE`, `whsec_EXAMPLE`).

## 11. Testing

Vitest, no network in the default suite.

| Area | Approach |
| --- | --- |
| Resources | Injected fetch mock asserting method, URL, headers, query, and body per operation — all 62 |
| Auth | Key present everywhere; **absent** on the four `/checkout/*` operations |
| Errors | Each status → correct subclass, with `code` and `correlationId` preserved |
| Retries | Fake timers: backoff sequence, `Retry-After`, no retry on non-idempotent POST without a key, cap respected |
| Idempotency | `create*` generates a key; caller's key wins; retry reuses the same key |
| Webhooks | HMAC vectors ported from `example_psp/src/webhooks/webhooks.controller.spec.ts`: valid, wrong secret, stale timestamp, malformed signature, both header spellings |
| Adapters | Supertest against a real Express app (raw body captured with and without `express.json()` mounted first); Nest testing module for the guard and decorator |
| Types | `expectTypeOf` narrowing tests for the event union and `Page<T>` |

CI: lint, typecheck, test, build, and `npm run codegen -- --check` to fail if
generated types are stale. A separate opt-in nightly job runs a smoke test
against the sandbox with a key from CI secrets.

## 13. Open questions

None blocking. Two to revisit during implementation:

1. The hand-modelled types for the 32 undocumented responses should be verified
   against real sandbox responses before `1.0.0`, and the findings fed back to
   the Chari Pay team so `api-1.yaml` can be completed.
2. `GET /v1/transactions` accepts both `cursor`/`limit` and a Spring `pageable`
   — confirm against the sandbox which one the server honours, and expose only
   that one.
3. `apiKey` is required by `ChariPayConfig`, yet the four `/checkout/*`
   operations never send one. An integrator using only the direct-API checkout
   is forced to supply a key it will not use. Decide during implementation
   whether `apiKey` becomes optional, with any keyed call throwing a clear
   `ChariPayAuthenticationError` explaining the omission.
